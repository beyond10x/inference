# Review of the inference design, v0.2

Reviewed: `docs/design/inference.md`, version 0.2, dated 2026-10-16, 1276 lines. Reviewed on
2026-10-18 against the beyond10x workspace: the `llm` repository at 0.6.0, `llm-gateway` at 0.12.0,
`loom`, `thalamus`, and the workspace rules in the parent `AGENTS.md`. No code exists; this is a
review of the document and of the plan it implies. Section references (§) are the document's own.

## Verdict

The architecture holds. The plan it implies does not yet. The document names nouns without a typed
home, re-proposes two things the workspace already has, and leaves open the questions its first
three stages depend on. Each is fixable in the planning store before any crate is created; the
proposals below do that.

## What the document gets right

These are kept as written. The plan builds on them.

- §1.2 and §8.1: streaming is four distinct capabilities, and a persistent connection proves none
  of them. This is the document's core contribution.
- §11: provisional, committed and irreversible as three classes, with §11.3's default commit
  rules. It is a state machine and can be specified as one.
- §7.5 and A-06: a native speech model is one multiport node, never three fake components.
- §5.3 and §24.1: start small; a six-step demonstrator is the success criterion, not a crate
  inventory.
- §16.4 and §21.3: no implicit cloud fallback, ever.

## Findings

### F1. The text-LLM path duplicates `llm` and `llm-gateway`

Evidence. The §5 tree proposes `inference-llm`, `inference-vllm`, `inference-openai`,
`inference-anthropic` and `inference-google`; §18 adds hosted text-LLM adapters; §24 schedules them
as P7. Neither existing repository is named anywhere in the document. `llm` 0.6.0 is "Rust libraries
for calling language models through one neutral interface, `Model::turn`", with the Responses,
Messages and Chat Completions wires, routing with fallbacks, an injected credential resolver and
cost accounting (`../../../llm/README.md`, lines 3 to 6). Its `b10x-llm-core` carries "neutral
model requests, results, streaming, capabilities and typed failures"
(`../../../llm/website/docs/reference/crates.md`, line 20). Fourteen crates sit under
`../../../llm/crates`. `llm-gateway` 0.12.0 is "the serving side of llm: an authenticated gateway
for one owner, and a hosting contract with Runpod and Modal adapters"
(`../../../llm-gateway/README.md`, lines 3 to 6).

Consequence. Five crates and one roadmap stage of the document are already built elsewhere.
Building them again here splits provider knowledge across two repositories.

Decision (owner, 2026-10-18): not acted on. `inference` is a composition library whose core carries
no concrete implementation, and the plan treats `llm` and `llm-gateway` as absent. The document's
split stands: `inference-llm` is a contract crate, and every concrete integration is a separate
adapter crate below it. An adapter over `llm` may be written later, or `inference` may replace
`llm`; neither is planned here.

### F2. Tool authorization and execution duplicate Loom

Evidence. §15.1 places schema validation, authorization and confirmation, a tool executor and human
confirmation inside `inference-tools`; §21.2 adds per-tool permission gates. Loom "is the runtime
for governed agents. It lets a model act as an agent for one bounded run, and only through the
actions a governed frontier admits at that moment"; Commission "rechecks the proposal against the
frontier, the case revision and the authority it needs, and only then hands it to an effect port"
(`../../../loom/README.md`, lines 3 to 4 and 22 to 26). `llm`'s README states the same split from
the other side: "llm never runs a tool. A caller such as Loom runs the loop and executes the tools
the model asks for" (`../../../llm/README.md`, lines 17 to 19).

Decision (owner, 2026-10-18): not acted on. The plan treats Loom as absent, and tool calling is
expected to leave Loom for a repository of its own. `inference-tools` stands as §15 writes it: the
tool contract (identities, schemas, proposal, authorization, execution and result events,
correlation, side-effect classes), with executors as adapters or testkit mocks below it. An adapter
to whatever repository ends up owning tool execution may be written later; it is not planned here.

### F3. Nouns with no typed home

Evidence. §3 defines ten concepts; §6.2 an envelope of twelve fields; §8.1 nine capabilities;
§11.1 and §11.2 the span and output states; §12.2 the run states; §15.1 the tool-call states;
§17.2 a capability record; §21.1 four deployment profiles. None is declared in a specification.
The workspace rule: "A new noun gets its ESS domain before any AEP story is written around it"
(parent `AGENTS.md`, "ESS drives every product repository").

Consequence. Under that rule not one story can be drafted until the domain exists. §27's Q1 (which
types live in core versus text, audio and domain crates), Q2 (async traits, node descriptors, or two
layers) and Q3 (the minimum event vocabulary) are the questions a domain document answers by being
written.

Proposal. Before any epic is decomposed, draft the ESS domain `inference`: the entities Model,
Adapter, CapabilityDescriptor, Node, Port, Edge, Pipeline, Run, Generation, Span, ToolCall,
Session and DeploymentProfile; their relations with cardinality; commands and views for the §11
state machine and the §8.3 negotiation. Q1 closes because an entity's crate follows its domain, so
the crate split is read off the document. Q2 closes as two layers: the node descriptor is the ESS
entity, the Rust trait is a projection of it. Q3 closes per scenario: the vocabulary is what the
first conformance scenarios need and grows with them, never ahead of them. A relation the document
does not settle is filed as an `UNMAPPED:` marker, not guessed. The store records the domain as
`executable-system-specification:inference`, whose ladder is draft, validated, conforming.

### F4. Open questions that gate the first stages are left open

Evidence. §27 lists fifteen questions "intentionally left unresolved". Q1 to Q3 gate P0 (§24).
Q9 (reference hardware), Q10 (permitted weight licenses) and Q11 (first two adapters) gate P2.
Q15 (the evidence required to claim `native_duplex`) gates P5, P6 and A-07.

Proposal. Q1 to Q3 close with F3. Q9, Q10, Q11 and Q15 become `decision-blocker` artifacts with a
`blocks` edge to each epic they stop and a default each:

| question | blocker | default on silence |
|---|---|---|
| Q9 reference hardware | `reference-hardware` | the machine at hand, named in the blocker once known |
| Q10 weight licenses | `weight-licenses` | code under Apache-2.0 or MIT; weights under CC BY 4.0 or more permissive; verified per checkpoint as §17 requires |
| Q11 first adapters | `first-adapters` | F6 |
| Q15 native-duplex evidence | `native-duplex-evidence` | one scenario: an output event is emitted after an input event that arrived during the same generation, from the same model instance, with no restart |

Q4 to Q8 and Q12 to Q14 do not gate P0 to P3 and stay in the document.

### F5. Roadmap and acceptance are prose, not scenarios

Evidence. The document carries 42 MUST, 12 MUST NOT, 22 SHOULD and 27 MAY (counted by grep). §23
lists six contract tests, seven adapter checks, eight runtime tests and fourteen acceptance rows
A-01 to A-14. None names a scenario. P0, P1 and P2 are all marked "First" in §24.

Proposal. Plan by §24.1's six demonstrator steps, not by the crate inventory or the stage number.
Each story's acceptance is a set of named conformance scenarios, and each A-nn row maps to at least
one of them. The first conformance targets are §11.3 (commit rules) and §8.3 (effective-capability
negotiation): every later stage depends on them, and both are checkable with mock nodes and no
model.

### F6. The adapter inventory is wider than the document's own rule

Evidence. The §5 tree names nine adapter crates; §17 lists eleven candidates; §5.3 says "two or
three adapters"; Q11 is open.

Proposal, as a recommendation that Q9 decides. P2 uses sherpa-onnx for STT, TTS and VAD (one
toolkit, one FFI boundary, runs on CPU) and `llm` against a local llama.cpp server for the LLM.
The second backend for §24.1 step 6 is whisper.cpp for STT or Piper for TTS. Kyutai streaming STT
and TTS and Moshi arrive in P5, where native streaming and duplex are the point. Code and weight
licenses are verified at adoption per §17; none is assumed here.

### F7. Minor

- §5 tree: a root `tests/` split into contracts, adapters, pipelines and integration. In a Cargo
  workspace these are per-crate `tests/` plus `inference-testkit`. Drop the root directory.
- §5 tree: `LICENSES/`. Workspace repositories carry one `LICENSE` (Apache-2.0); third-party
  notices arrive with the first adapter that needs them.
- §16.1 names Python subprocess workers. Workspace rule: anything committed that runs is Rust
  (parent `AGENTS.md`, "Running code is Rust"). A worker in another language is an external process
  behind §16.2's protocol, never a file in this repository. This repository's `AGENTS.md` says so.
- §20: the metrics table names no consumer. `thalamus` describes itself as "the realtime perception
  layer: typed signals, samples and verdicts over the systems an organization runs"
  (`../../../thalamus/.engineering/project.yaml`). Whether it is the consumer was not checked.

## Not checked

  reuse.
- Whether `thalamus` is the intended consumer of §20's metrics.
- The licenses of the candidate backends in §17.
